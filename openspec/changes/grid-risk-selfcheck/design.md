# 设计：风控完整性自检与启动摘要

## 事故复盘

Lighter 裸奔了整整一天，没有任何信号。它的启动日志是：

```
Lighter 做市启动：标的=BTC，档位=每边10，每格金额=$300，库存上限=$3750，
格距=0.000986，轮询间隔=2.5秒，慢路径=30秒，dry_run=False
```

**一个字都没提风控。** 而 Extended 同期在日志里持续输出 `trend-aware mark=...
frozen=True band=[...]`，两者差异肉眼可见却无人对比。

更隐蔽的是能力探测：

```python
balance_getter = getattr(self.ext, "get_balance", None)
if not callable(balance_getter):
    return False          # 净值熔断，静默
```

`getattr` 探测 + 静默降级，本意是「适配器能力不同，缺了就跳过」，实际效果是
**风控可以在无人知情的情况下整层消失**。

## 关键决策

### 1. 风控层与依赖能力的显式映射

把「哪层风控需要哪些适配器能力」从散落的 `getattr` 提升为一张显式表，
自检与运行期告警共用同一张表。散落的探测点无法枚举，也就无法审计。

| 风控层 | 依赖能力 | 缺失后果 |
|---|---|---|
| 净值回撤熔断 | `get_balance` | 整层失效 |
| 整仓 TPSL 权益约束 | `get_balance` | 退化为仅清算缓冲 |
| 硬止损 / TPSL 清算约束 | `get_liquidation_info` | 退化为仅按距离 |
| 趋势 band 保护 | K 线源 + `trend_aware=True` | 无区间概念，趋势中无限加仓 |

### 2. 缺失即拒绝启动，而不是降级

**这是本设计的核心取舍。** 现状是「缺了就跳过」，代价是可以裸奔；改为
「缺了就不让跑」，代价是配置不全时机器人起不来。

选后者：网格是**做空 gamma** 结构，尾部行情里风控是唯一的保命装置。
一个跑不起来的机器人损失的是机会，一个没有风控的机器人损失的是本金——
2026-08-19 已经证明了后者的代价。

### 3. 但必须允许「知情放弃」

不能让自检变成无法绕过的墙：dry-run 调试、新交易所接入初期、只读适配器等场景
都可能合法地缺能力。因此提供显式开关声明放弃某层风控，此时以 WARNING 放行。

**关键是让放弃成为一个显式的、留痕的动作**，而不是像现在这样「什么都不写
就自动没有」。默认必须是安全的一侧。

实现接口使用可重复的 `--waive-risk <layer-id>`，其中 `layer-id` 为
`equity_drawdown`、`position_tpsl_equity`、`liquidation_constraints` 或
`trend_band`。未传时配置为一个空元组，表示不放弃任何层。三个事故相关 flag
（`--trend-aware`、`--max-drawdown`、`--hard-stop-dist`）还会记录是否真的出现在
CLI 中，避免配置对象的历史默认值把「运维未显式配置」伪装成已确认启用。
即使 TPSL 仍使用清算价约束，`hard_stop_dist <= 0` 也会被标记为硬止损
「部分关闭」并默认拒绝，避免另一条清算保护掩盖硬止损已关闭；显式放弃该层后方可放行。

两个入口同时提供 `--risk-selfcheck-only`：只构造适配器做结构能力检查，不调用
`connect()`、账户查询或交易循环；Lighter 在此模式下不会启用签名器，也不要求
交易私钥。该模式用于安全回放 plist 参数和部署前审计。

### 4. 启动摘要必须逐层列出，包括「关闭」的层

只打印启用的层没有意义——这次的问题恰恰是**没启用的层没人注意**。摘要要把
每一层都列出来，关闭和不可用的用醒目标记，让一眼扫过去就能发现异常。

摘要是给人看的，不是给机器看的，所以宁可啰嗦。

### 5. 运行期告警要限频

风控在轮询中每 2.5 秒检查一次，能力缺失时若每轮告警会淹没日志（参考本次
「库存上限拒绝挂单」一天刷了上万条）。按状态变化 + 整百次聚合输出，
与既有 `_log_cap_rejection` 的做法保持一致。

### 6. `get_balance` 的返回形状

引擎两处都按 `balance.get("equity")` 或 `getattr(balance,"equity",None)` 取值，
因此新方法只需返回带 `equity` 的对象或 dict 即可，无需改动引擎取值逻辑。

Lighter 侧 `get_collateral()` 已能拿到抵押品数值。需要注意的是**抵押品与权益
未必等价**（未实现盈亏是否计入），实现时必须核对 Lighter 账户接口的口径，
并在文档字符串里写明该口径——口径错了会让熔断在错误的位置触发，比不触发更危险。

实现核对结论（2026-08-20）：Lighter 官方文档将 Total Account Value 定义为
`Collateral + Unrealized PnL`，账户详情响应对应字段为 `total_asset_value`；因此
`get_balance()` 使用该字段作为 `equity`，明确包含未实现盈亏，不复用仅表示抵押品的
`collateral`。查询失败、字段缺失或数值无效时抛出，不合成零权益。参考：
https://docs.lighter.xyz/trading/pnl-and-total-account-value

## 不做

- 不改任何风控的**阈值与算法**（12%、10%、band_k 等一概不动）。
- 不自动修改 plist。自检通过后由人工补 flag，保持「本仓库任务不执行 launchctl」
  的既有约定。
- 不引入 `wallet_exposure` 相对化（`max_inv` 绝对值 → 权益比率）。那是独立的
  策略变更，虽然同样由本次事故暴露（Lighter 权益 ~$730 时 $3,750 上限 = 5.1x，
  Extended ~$960 时 = 3.9x），但须单独提案。
