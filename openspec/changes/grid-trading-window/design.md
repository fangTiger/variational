# 设计：网格交易时段窗口

## 实证依据

83 天 BTC-USD 小时线（2000 根），按 UTC+8 小时聚合：

```
时段            平均振幅    趋势性    >1.5%小时占比   >2%小时占比
05:00-20:00     0.470%     0.497        0.80%          0.24%
20:00-05:00     0.629%     0.502        2.54%          1.07%
倍数             1.34x     1.01x        3.17x          4.45x
```

**趋势性几乎相同（1.01x）是关键**——它排除了「夜间更容易走单边」这个直觉解释。
真实机制是**尾部分布更厚**：均值只差 1.34 倍，2 个标准差外差 4.45 倍。

振幅最高的四个小时依次是 23:00(0.816%)、21:00(0.815%)、22:00(0.803%)、
20:00(0.648%)，全部落在待停窗口内；最低的 18:00(0.366%)、19:00(0.397%)
则在运行窗口内。

## 关键决策

### 1. 停机必须平仓，不是只停机器人

**这是本设计的成立前提。** 2026-08-19 的亏损全部来自持仓过夜——若 20:00 只停
进程、留着 −$1,800 库存，那波 8.5% 暴涨照样打在身上，整个机制毫无意义。

离场序列必须是：**撤单 → 平仓至零 → 停止开仓**，三步缺一不可。

### 2. 进程保持运行，不退出

窗口外让进程空转而非退出，理由：

- launchd `KeepAlive` 会立刻重启退出的进程，与「计划内停机」语义冲突，
  容易演变成重启风暴
- 保持运行才能继续输出心跳，否则告警系统会把计划内停机误报为故障
  （这次停机后 `alert-check` 就在误报，只能连它一起停掉）
- 05:00 自愈恢复，不依赖任何外部调度器

比用 launchd 定时启停可靠得多——后者还要处理启动时的状态接管。

### 3. UTC+8 硬编码，不读本机时区

用固定偏移计算，不依赖 `TZ` 环境变量或系统时区设置。理由：本机时区可能被改动
或在迁移时变化，而交易时段是策略参数，不该随部署环境漂移。

夏令时不影响：UTC+8 无夏令时。美股夏令时会让美东开盘在 UTC+8 的 21:30 与 22:30
之间移动，但两者都落在停机窗口内，不影响判定。

### 4. 平仓用 maker 优先、超时转市价

Extended maker 费为 0，直接吃单是纯浪费。复用项目已有的
`--maker-first-timeout` 模式（见 `deploy/com.variational.lighter-hedge.plist`）：
先挂 post-only 限价单，超时未成交则撤单并用市价补齐未成交部分。

**但超时后必须转市价。** 「maker 挂着等成交」在这里是不可接受的失败模式——
平不掉就等于留仓过夜，机制失效。宁可付 taker 费。

### 5. 平仓失败必须持续重试并告警

网络故障、接口异常都可能让平仓失败。此时**绝不能静默进入停机状态**——那会
留下一个无人管理的裸仓，正是 8/19 的形态。必须持续重试并告警，直到归零。

### 6. 窗口外启动时也要平掉接管的库存

进程可能在停机窗口内被重启（崩溃恢复、人工操作）。此时 `connect()` 会接管账户
已有仓位。为保持「停机时段无仓位」这一不变量，接管后应按同一规则平掉。

### 7. 计划内平仓不得触发熔断的 halted

离场平仓是计划内动作，与硬止损、净值熔断的「一次性 kill switch」语义不同，
不应写入 `halted` 或要求人工复位。两者的代码路径必须分开。

## 成本与已知代价

- **每日一次强制平仓的 taker 成本**：Extended taker 0.0225%，按 $2,000 仓位
  约 $0.45/天、约 $164/年。maker 优先能削减一部分，但不能假设总能成交。
- **放弃夜间闭环利润**：夜间振幅是白天 1.34 倍，且占 9/24 小时，粗估放弃约
  40% 的闭环机会。这是本设计**明确接受**的交换。
- **强制平仓时点可能不利**：20:00 硬平会锁定当时浮亏。用确定的小成本换不确定
  的大尾部，是本设计的核心取舍。

## 未来可能的升级（本次不做）

「夜间只减仓不开新仓」：保留反向闭环的回收能力，不扩大敞口，可省下每日平仓成本
并保留夜间震荡收益。引擎已有 `_maintain_recovery_ladder` 的 reduce-only 语义可复用。

先做完全停机版，因为它语义明确、可靠，且能直接验证「避开尾部」这个假设是否成立。
积累一两个月数据后再评估是否升级。

## 不做

- 不区分工作日与周末（用户明确要求每天同一时段）。
- 不改动库存上限、熔断、TPSL、趋势 band 的阈值与算法。
- 不自动修改 plist；启用由人工在验收后配置。
