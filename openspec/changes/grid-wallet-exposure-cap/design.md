# 设计：库存上限改为按权益比例

## 问题的实证

2026-08-19 停机时的两组数字：

| | 权益 | `max_inv` | 实际杠杆 |
|---|---|---|---|
| Extended | ~$960 | $3,750 | 3.9x |
| Lighter | ~$730 | $3,750 | **5.1x** |

同一个 3750 在两个账户上是两种风险。而这个数字的来源是照抄——
`run_lighter_mm.py` 的注释写着「与实盘 Extended 网格的 --max-inv 3750 对齐」，
**对齐的是数字，不是风险**。

更糟的是过程：Extended 权益从峰值 $1,007 跌到 $899 的整个过程中，上限纹丝不动，
实际杠杆被动从 3.7x 升到 4.2x。**正该收缩敞口的时候它在放大。**

## 关键决策

### 1. 取「权益 × 比例」与「绝对硬顶」中更紧者

不是用比率**替换**绝对值，而是两者并存取 `min`。

比率负责随权益自动缩放，绝对硬顶负责兜底——防止权益读数异常偏大（接口口径变化、
入金、脏数据）时上限失控。这与 `_maintain_tpsl` 已有的「多约束取更紧」风格一致。

### 2. 权益口径用含未实现盈亏的那个

沿用 `grid-risk-selfcheck` 已核实的结论：Lighter 的
`total_asset_value = Collateral + Unrealized PnL`；Extended 用 `BalanceModel.equity`。

**必须含未实现盈亏**，否则失去本变更的核心价值：库存浮亏 → 权益下降 →
上限收紧 → 更早停止加仓。这条负反馈正是 8/19 缺的东西。

代价是上限会随价格波动抖动。缓解手段见下一条。

### 3. 复用净值熔断的权益缓存，不额外增加请求

权益查询已有限频（`_EQUITY_CHECK_INTERVAL_S`）。上限计算复用同一份缓存值，
**不新增任何请求**——Lighter 的写操作限流是 40 req/60s，只读虽不占该额度，
但没有理由为此多打接口。

限频本身也顺带平滑了上限抖动：上限每 N 秒才更新一次，而非逐轮跳动。

### 4. 权益不可用时退回绝对硬顶，绝不放行

**这是安全方向的关键取舍。** 读不到权益时有三种可能做法：

- 放行不限制 → 绝对不行，等于无上限
- 拒绝一切挂单 → 过激，网格会因一次接口抖动完全瘫痪
- **退回绝对硬顶** ← 采用

退回硬顶意味着退回当前行为（现状就是纯绝对值），是安全的下界。同时限频告警，
让「比例保护当前没在生效」这件事可见——这正是 8/19 静默失效的教训。

### 5. 已有库存超过新上限时，只阻止同向新增，不强制平仓

权益下跌会让上限收缩到当前库存之下。此时**不主动平仓**。

理由：强制平仓会在震荡中反复触发（权益随浮亏波动 → 上限反复穿越库存 →
平仓 → 又开仓），既产生实亏又制造 taker 成本。而「只阻止新增」是单调的：
敞口只能减不能增，靠网格另一侧的成交自然回落。

真正需要主动减仓的场景已由既有的净值熔断与硬止损覆盖，不该在这里重复实现。

### 6. 未配置比例时行为与现状完全一致

比例参数不传 = 只用绝对值 = 当前行为。这保证变更可以先上线、后启用，
也让 Extended 和 Lighter 可以分别按各自节奏切换。

## 与 `grid-risk-selfcheck` 的关系

本变更**依赖**前一变更引入的 `get_balance()`。且一旦启用比例上限，
`get_balance` 就从「熔断与 TPSL 的依赖」升级为「库存上限的依赖」——
应纳入风控自检的依赖映射，缺失时按同样规则拒绝启动。

实施顺序：`grid-risk-selfcheck` 必须先落地。

## 首次启用值：3x（2026-08-20 用户决定）

机制本身比例可配，本节只记录首次启用的取值与依据。

停机时的实际杠杆：

| | 权益 | `max_inv` | 实际比例 | 3x 后的上限 |
|---|---|---|---|---|
| Extended | $899.46 | $3,750 | **4.17x** | $2,698（收紧 28%） |
| Lighter | $729.76 | $3,750 | **5.14x** | $2,189（收紧 42%） |

依据：早期放大仓位时定过「~2.75x 上限，因为网格已偏激进」，后来一路放到 4~5x，
8/19 正是在这个杠杆上被 8.5% 单边行情打穿。3x 是回到当初的判断。

**但必须写明 3x 本身扛不住 8/19 那种行情**：3x 满仓（Lighter $2,189）遇上 8.5%
单边，方向亏损约 $186 ≈ 权益的 25%。真正截断损失的是 **12% 净值熔断**——而它
在 Lighter 上此前从未生效（`get_balance` 缺失，见 `grid-risk-selfcheck`）。

> 3x + 熔断真的生效 = 有效保护；3x + 熔断仍失效 = 只是亏得慢一点。

这也是两个变更顺序不可颠倒的原因。

**推荐启用节奏**：先在 Extended 单边启用并观察，再推到 Lighter。Extended 的风控栈
已通过自检验证（四层全绿），Lighter 的 `get_balance` 是新补的能力，宜先在
「自检 + 熔断 + 绝对上限」状态下积累数据，再叠加比例上限。

## 不做

- 不改 `_within_cap` 的判定语义（仍是「真实持仓 + 同侧挂单全成交后不得超限」），
  只改上限数值的来源。
- 不引入 Passivbot 式的 `ddown_factor`（亏损时加倍仓位）——与现有三层风控冲突，
  且账户规模扛不住。
- 不改动其他风控的阈值与算法。
