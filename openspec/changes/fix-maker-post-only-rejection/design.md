## Context

`maker_first_hedge` 在挂单前保存 hedge 腿仓位基线，随后调用统一的 `place_limit_order(..., post_only=True)`。Hyperliquid SDK 0.24.0 的 `Exchange.order()` 会原样返回包含 `statuses[0].error` 的业务响应，`HyperliquidClient._order_result()` 再把该字段转换为 `RuntimeError`。因此 post-only 立即成交拒绝发生在取得订单 ID 之前，现有撤单、订单重读与仓位差降级逻辑无法接管。

## Goals / Non-Goals

**Goals:**

- 只把可预期的 post-only 立即成交拒绝转换为市价补差。
- 所有补单数量由挂单前后真实仓位变化计算。
- 保持无关错误向上抛出，并保持正常 maker 路径不变。

**Non-Goals:**

- 不改变网格、风控、轮转状态机或其他适配器。
- 不在本次修复中调整 Hyperliquid 调用方传入的限价。单纯偏移一个 tick 仍不能消除报价读取后的竞态，且会改变通用限价接口的价格语义。

## Decisions

### 在执行引擎边界识别并降级

采用引擎层的窄异常分流：规范化异常文本中的大小写和连接符，识别 post-only/maker-only 拒绝或立即撮合、穿价、吃流动性等语义。命中后重读仓位，按 `target_delta - (position_after - position_before)` 计算剩余变化量，仅在仍与原目标同方向时吃单；未命中则原样重新抛出。

备选方案一是只在 Hyperliquid 适配器中把价格外移一个 tick。它只能降低概率，无法关闭行情快照与下单之间的竞态，也不能保护其他会拒绝 post-only 的交易所。备选方案二是把所有挂单错误都降级为市价单，这会误吞余额、权限、精度和连接错误，扩大实盘风险。因此均不采用。

### 复用既有仓位差安全原则

拒绝响应没有订单 ID，不能查询或撤销订单；但挂单前仓位基线已经存在。降级路径必须再次读取真实仓位，并复用既有“只补同方向剩余差值”的保护，避免在并发成交或仓位变化时按原委托量产生双倍对冲。

## Risks / Trade-offs

- 错误文案来自不同交易所，识别过窄会漏降级，过宽会误吞错误。通过“post-only 标记 + 拒绝语义”或明确的“立即撮合/穿价/吃流动性”片段组合，并用无关错误回归测试限制边界。
- 拒绝后仓位重读自身也可能失败。此时没有可靠补单量，异常继续向上抛出，保持保守失败。
