## 一、背景与证据

### 1.1 头号漏损：35% 的消失订单判不出终态（有日志实证）

统计 `log/grid_engine_2026072[7-9].log` 与 `20260730.log`（已剔除单测污染行）：

| 日期 | 终态=未知 | 真实翻单 | 未知占比 |
|---|---|---|---|
| 07-27 | 1 | 14 | 7% |
| 07-28 | 30 | 80 | 27% |
| 07-29 | 13 | 7 | 65% |
| 07-30 | 35 | 42 | 45% |
| **合计** | **79** | **143** | **35%** |

当前代码路径（`grid/grid_engine.py:801-840`）：订单从盘口消失 → `_order_statuses()` 查终态 → 查不到就 `status_pending=True` 并 `continue`，**该档位被无限期冻结**（`_maintain_ladder` 在 `grid_engine.py:925-927` 会跳过 pending 档不补单）。

**后果链**：真实成交判不出 → 止盈腿永远不挂 → 这一格的利润归零，且该档位从网格中永久消失 → 网格逐格稀疏 → 收益趋近 0。这与实盘现象一致（12 天 PnL −$1.32）。

### 1.2 根因假设（**必须先验证，不得直接照假设改**）

参考实现 `src/exchange/ex/extended.js:400` 的原文注释：

> A FILLED order is NOT returned by the open-orders endpoints — once it fills it moves to ORDER HISTORY. So confirm via history (filtered by order id), which carries the terminal status + filledQty + averagePrice.
> **(Querying the open-orders-by-id path could never see a real fill, which previously made every Extended fill look "unconfirmed" and dropped its take-profit replacement.)**

我们的兜底 `adapters/extended_client.py:368-372` 用的正是 `account.get_order_by_id(order_id)`。**假设**：该端点查的是活动订单，已成交单查不到 → 返回 None → 判为未知。批量历史 `get_orders_history(limit=100, order_type="LIMIT")` 能命中的就成功（那 143 笔），落在 100 行窗口外的就变成未知（那 79 笔）。

**Task 2 的第一步就是证伪或证实这个假设，不允许跳过。**

### 1.3 已被证据否定的假设（记录在案，避免重复走弯路）

原以为 `post_only=True` 导致翻单被拒是主因。**实盘日志里真实 `REJECTED` 为 0 次**（`grep` 命中的 40 条全部来自单测写进 `log/grid_engine_*.log` 的污染数据，价格 88/100）。因此 **post_only 本批不改**，只加埋点测量，等数据说话。

### 1.4 次级漏损

- **轮询 30s**：参考实现是 `pollMs = 2500`（`extended.js:41`）+ 独立 30s 对账（`bot.js:9`）。BTC 30 秒常走 0.1%，我们的止盈腿总是慢一拍挂在已跑掉的价位。
- **挂单有效期 7 天**：参考实现 `ORDER_EXPIRY_DAYS = 90 // max GTT; longer = less decay on long-running grids`（`extended.js:26`）。

背景（2026-07-30 实盘统计）：222 笔从盘口消失的订单里 79 笔（35%）查不出终态，

from types import SimpleNamespace

from adapters.base import Side
from grid.grid_engine import GridConfig, GridEngine


class HistoryOnlyExt:
    """桩：by-id 端点看不到成交单（返回 None），但历史里有 FILLED 记录。"""

    def __init__(self, history, history_limit_seen=None):

        self.history_limit_seen = history_limit_seen if history_limit_seen is not None else []
        self.placed: list[dict] = []

    async def get_open_orders(self, market):
        return []

    async def get_orders_history(self, market, limit=100, **kwargs):

    return SimpleNamespace(id=oid, status=status, filled_qty=filled_qty)


def test_filled_order_beyond_batch_window_still_resolves() -> None:
    """成交单排在历史窗口靠后时，仍必须判定为成交并翻单（不得判未知）。"""

    assert eng._orders[558].get("status_lookup_attempts", 0) == 0, "重试计数必须清零"

在 `adapters/extended_client.py` 新增按 id 在历史中查找的方法（替代不可靠的 by-id 端点）：

```python
    async def find_order_in_history(self, market: str, order_id, *, limit: int = 200):
        """在订单历史中按 id 查找单笔订单（含终态 status/filled_qty）。

        背景：活动订单端点查不到已成交单——订单一旦成交就移出活动列表、
        只存在于历史里。网格判定成交必须走历史，否则每笔成交都会被判为
        "终态未知"，止盈腿丢失。
        """
        rows = await self.get_orders_history(market, limit=limit, order_type="LIMIT")
        target = str(order_id)
        for row in rows:
            if str(getattr(row, "id", "")) == target:
                return row
        return None
```

在 `adapters/base.py` 补契约声明（与既有风格一致）。

改 `grid/grid_engine.py` 的 `_order_statuses`：批量历史 `limit` 由 100 提到 200；未命中的订单**优先**用 `find_order_in_history` 兜底，仅当适配器没有该方法时才退回 `get_order_by_id`。

改 `_handle_fills`（`grid_engine.py:806` 起）：当查到的状态属于活单状态（`NEW` / `OPEN` / `ACCEPTED` / `PARTIALLY_FILLED` / `UNTRIGGERED`）时，判定为盘口坏快照——**清零** `status_lookup_attempts`、清除 `status_pending`、保留跟踪、不做任何挂撤单动作。（参考实现 `extended.js` 的原文：`counting these toward the give-up threshold used to drop dozens of perfectly live orders during an API hiccup`。）

### Task 3：双层轮询节奏（主循环 5s + 重指标 30s 缓存）

**设计**：不引入并发。保持单主循环，把间隔从 30s 降到 5s，把**每轮都跑但 5s 内不会变**的重活加 TTL 缓存：

| 每轮（5s） | 缓存 30s |
|---|---|
| `_handle_fills`（成交判定 + 翻单） | 1H K 线拉取 `get_candles_history` |
| `_maintain_ladder`（补格/撤陈单） | ADX / 斜率 / ATR / regime 判定 |
| 库存与 mark 读取 | band 推进 `_advance_band` |
| | `_maintain_tpsl` |

理由：1 小时 K 线在 5 秒内不可能变化，重复拉取纯属浪费并会撞限频；而成交检测每慢一秒，止盈腿就多偏离一点。参考实现同样是双层（`extended.js:41` `pollMs=2500` + `bot.js:9` `RECONCILE_MS=30000`）。
