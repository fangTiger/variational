# 统一监控面板 设计文档

## 背景与目标

**目标：让用户不问 Claude 就能自助掌握所有实盘系统的现状。**

现状是 `tools/grid_panel.py`（557 行，端口 8787）只覆盖 BTC 网格。系统已经增加到两个（网格 + Lighter RH 积分对冲），归因数据层也已就绪，用户明确表示**还会继续增加系统**。

因此本次设计的首要指标不是"把对冲加上去"，而是**加第 N 个系统的成本要足够低**。

## 关键约束（用户已确认）

| 项 | 决定 |
|---|---|
| 页面结构 | 总览条 + 每系统一张卡片 + 告警区 |
| 告警呈现 | 每条告警**必须带动作指引**，说清去哪儿、改什么 |
| 交互 | **只读**。不做"一键处理"按钮——面板一旦能动真钱，误点就是真实交易 |
| 访问范围 | 仅本机 localhost:8787，桌面布局，不做响应式、不暴露局域网 |
| 刷新 | 整页 5 秒自动刷新，与现状一致 |

## 架构：数据源注册表

核心思路是把**取数**和**渲染**彻底分开。每个系统提供一个 provider，职责单一：读本地文件 → 返回统一结构。渲染器只认这个统一结构，不知道也不关心背后是网格还是对冲。

```
tools/grid_panel.py       入口 + HTTP 服务（瘦身为只做路由）
panel/
  types.py                SystemStatus / Metric / Alert 数据类
  render.py               纯函数：list[SystemStatus] → HTML
  registry.py             provider 列表，加系统就在这加一行
  providers/
    grid.py               读 data/grid_live.json + data/grid_monitor.jsonl
    hedge.py              读 data/lighter_hedge.jsonl
    attribution.py        读 data/fills.jsonl 现算
```

**加一个新系统的完整成本**：新建一个 provider 文件（约 50 行）+ 在 `registry.py` 加一行。渲染器、HTTP 层、样式一律不动。

### 为什么不用配置驱动

考虑过用 YAML 描述"读哪个文件、显示哪些字段"，否决了。网格有 band / regime / 熔断距离，对冲有两条腿 / 净敞口 / 名义上限，形状本质不同。硬套统一配置的结果是配置里塞满特例，比直接写 Python 更难懂。provider 就是 Python 函数，需要什么逻辑写什么逻辑。

### 数据契约

```python
@dataclass(frozen=True)
class Metric:
    label: str
    value: str
    tone: str = "normal"        # normal / good / warn / bad

@dataclass(frozen=True)
class Alert:
    key: str                    # 与 alert_check 的 key 一致
    level: str                  # critical / warning / info
    title: str
    action: str                 # 该做什么——不可为空

@dataclass(frozen=True)
class SystemStatus:
    name: str
    alive: bool | None          # None = 该系统无"存活"概念（如归因）
    summary: str                # 卡片副标题，一句话
    metrics: list[Metric]
    equity: float | None        # 计入总览条的权益；None = 不计入
```

**告警是全局的，不挂在 SystemStatus 上。** `alert_check.collect_alerts()` 返回的是全局列表，且部分 key（如 `bot_down`、`no_success`）本就跨系统。强行把它们拆到各张卡片上，需要维护一张"key → 属于哪个系统"的映射，而这张表会随告警增加持续腐化。因此告警统一收集一次，渲染在页面底部独立的告警区——这也正是已确认的页面布局。

`equity` 字段的口径：网格取 Extended 网格账户权益；对冲取 **Lighter 抵押品 + Extended 对冲账户权益之和**（两条腿是一个整体，分开看会误导）；归因卡片为 `None`，不计入总览。

`Alert.action` **不允许为空**，这是刚性约束。用户明确说过"即使报警了，我也不知道需要做什么"——没有动作指引的告警对他没有价值，只会制造噪音并稀释真正要紧的那几条。

## 告警来源与动作映射

**不重新实现判定逻辑。** `tools/alert_check.py` 已有全部 18 类告警的判定，provider 直接调它现成的 `collect_alerts()`。

好处是面板和 macOS 通知**永远说同一件事**，不会出现面板显示正常、通知说有事的分裂。代价是面板依赖 alert_check 的内部函数，需要把 `collect_alerts()` 保持为稳定接口。

新增一张 `panel/actions.py` 映射表，把 18 个 key 翻译成动作指引：

| 告警 key | 动作指引 |
|---|---|
| `bot_down` | 网格引擎不在运行。告诉 Claude 重启，或检查 `logs/grid-bot.err.log` |
| `halted` | 净值回撤熔断已触发，已全平停机。需人工复位——告诉 Claude 处理 |
| `grid_blocked` | 网格单边被封（价格触及 band 边界），属正常保护，回到区间内会自动恢复 |
| `live_missing` / `live_stale` | 引擎快照未更新，可能卡死。告诉 Claude 检查 |
| `monitor_missing` / `monitor_stale` | 权益快照服务异常，不影响交易，但监控数据会断档 |
| `no_success` | 长时间没有成功下单，可能是 API 或余额问题 |
| `leverage` | 杠杆偏离预期，检查是否被手工改过 |
| `lighter_hedge_missing` / `lighter_hedge_stale` | 对冲机器人失联，**你现在可能裸敞口**。告诉 Claude 重启，或自己先平掉 Lighter |
| `lighter_hedge_net_delta` | 净敞口持续未收敛，对冲失效中。告诉 Claude 检查 |
| `lighter_hedge_notional_cap` | Lighter 仓位超过上限，机器人拒绝跟单。去 RH Wallet 减仓，或告诉 Claude 调高上限 |
| `lighter_hedge_primary_read` | 读不到 Lighter，引擎已停止动仓。检查网络或 API 状态 |
| `lighter_hedge_margin` | Extended 对冲腿保证金不足。加钱或减仓 |
| `lighter_hedge_invalid` | 心跳数据异常（字段缺失或时间戳错乱），机器人可能有 bug |
| `attribution_gap` | 归因账目对不上，**这批收益数字不可信**，不要用它做去留判断 |
| `verdict_stop` | 4 周判据结论为停止。告诉 Claude 复核后再决定 |

映射表必须覆盖全部 key。新增告警时若忘了加映射，渲染层显示"（缺动作指引）"并在测试中失败——用测试强制这张表不掉队。

## 归因数据的处理

用户已决定**不安装** `com.variational.pnl-attribution` 每小时服务，理由是残差告警对他不具备可操作性。

因此 `providers/attribution.py` 在页面加载时**现算**：输入全部是本地文件（`fills.jsonl` + `grid_monitor.jsonl`）加一次资金费 API 调用，是纯函数。

加 **5 分钟缓存**，避免 5 秒自动刷新把资金费接口打爆。

这样不装任何服务也能在面板上看到实时归因。归因卡片的 `alive` 为 `None`——它不是一个"进程"，没有存活概念。

## 错误处理

**面板的任何异常都不能变成白屏。** 用户依赖它判断实盘状态，一个打不开的面板比没有面板更危险——他会以为"没消息就是好消息"。

- 单个 provider 抛异常 → 该卡片显示为"数据读取失败"并附异常摘要，**其他卡片正常渲染**
- 数据文件缺失或损坏 → 按缺失处理，不抛异常（沿用现有 `_read_live` 的容错风格）
- 资金费 API 超时 → 归因卡片显示"资金费不可用"，其余归因字段照常显示
- 渲染层收到不认识的 `tone` 值 → 降级为 `normal`

## 测试策略

- `panel/render.py` 是纯函数，用构造好的 `SystemStatus` 列表测 HTML 输出，不碰文件系统
- 每个 provider 用临时目录里的假数据文件测，覆盖：正常、文件缺失、文件损坏、字段缺失
- **动作映射完整性测试**：遍历 `alert_check` 里所有 Alert key，断言每个都能在 `panel/actions.py` 找到非空动作指引
- 失败路径优先：先写"provider 抛异常时其他卡片仍渲染"的测试

## 迁移策略

`grid_panel.py` 是用户每天在看的面板，**改造期间必须一直可用**。

1. 新结构在 `panel/` 下独立建起来，旧 `grid_panel.py` 完全不动
2. 新增 `--new` 参数或临时端口，让新旧面板并存
3. 用户确认新面板显示正确后，再把 `grid_panel.py` 切成新实现的薄入口
4. 旧渲染代码在切换确认后才删除

## 明确不做（YAGNI）

- 不做一键操作按钮——只读是刚性约束
- 不做历史图表——现有面板没有，本次不引入
- 不做响应式/移动端布局——用户确认只在本机看
- 不做认证——不暴露到 localhost 之外，就不需要
- 不做告警历史归档——只显示当前活跃告警 + 最近一条已恢复记录
