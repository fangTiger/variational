# Lighter 做市刷量 + Extended 对冲 设计文档

## 背景与目标

**目标：在 Lighter 上跑做市网格产生真实成交量，赚取 volume 维度的 LIT 积分，同时用 Extended 对冲掉库存的方向风险。**

现状是 Lighter 上持有 $1,500 的静态多头仓位（手动开），只吃 OI 维度的积分。用户手动操作频率约 24 小时 2-3 单，日成交量约 $900，而 Lighter BTC 日成交是 $1.16 亿——**volume 这条赛道等于完全没参与**。

## 用户已确认的关键决定

| 项 | 决定 | 代价 |
|---|---|---|
| 账户 | 与现有 OI 仓共用同一个 Lighter 账户，**平掉现有手动仓** | **放弃 2x 乘数**，全押 volume 赛道 |
| 库存上限 | $1,500 | Extended 对冲腿 $465 权益需扛 $1,500 反向仓 |
| 实现路径 | 复用现有 `grid_engine` | 需要写完整的 Lighter 交易适配器 |
| 对冲下单 | 混合：先 maker，超时转吃单 | 复杂度最高，但成本最低且敞口最终必被覆盖 |
| 上线 | **跳过 dry_run**，直接 $300 实盘，12 小时无问题扩至 $1,500 | 见「首次实盘的额外约束」 |

## 架构：两个独立机器人

```
┌─ Lighter 做市机器人（新建）──────────────┐
│  复用 grid_engine，双边挂限价单           │
│  Lighter maker/taker 费率均为 0           │
│  产出：成交量（积分）+ 价差利润 + 库存     │
└──────────────────┬────────────────────────┘
                   │ 库存变化
                   ↓
┌─ Extended 对冲机器人（已在实盘运行）──────┐
│  读 Lighter 持仓 → Extended 镜像反向      │
│  改动：下单方式改为 maker 优先、超时吃单   │
└───────────────────────────────────────────┘
```

两个进程完全独立，通过「Lighter 账户持仓」这一共享状态耦合。对冲机器人不关心该持仓由谁产生，因此**现有对冲逻辑无需改动**，只改下单方式。

### 为什么网格和对冲不是二选一

网格负责赚积分和价差，对冲负责消除 BTC 涨跌风险。没有对冲，Lighter 网格就是裸的方向敞口——正是现有 Extended 网格的处境（此刻 -$1,609 库存无任何对冲，靠 12% 净值熔断兜底）。加上对冲后，库存被实时抵消，组合的 P&L 只剩价差捕获减去对冲成本。

## 对冲成本是本设计的核心经济约束

| 项 | 数值 |
|---|---|
| 每格金额 | $300 |
| 每个闭环毛利 | $300 × 0.0986% = **$0.296** |
| 每次对冲（吃单）成本 | $300 × 3bps ≈ **$0.09** |
| 一开一平两次对冲 | **$0.18** |
| 纯吃单方案净剩 | **$0.116（利润被吃掉 60%）** |

网格成交越频繁、对冲成本越高，而刷量的目标恰恰是提高成交频率。因此对冲下单方式直接决定这套系统能否回本。

**Extended maker 费率为 0**（现有网格全部用 post_only 限价单正是靠这一点盈利）。所以采用混合策略：

```
库存变化超阈值 → 挂 Extended 限价单（maker，费率 0）
                 ↓ 等待 15 秒（可配）
              已成交 → 完成
              未成交 → 撤单，转市价吃单（3bps）
```

15 秒的取舍：足够在正常行情下让 maker 成交，又不至于在单边行情里裸太久。该值必须可配。

## Lighter 交易适配器

现有 `adapters/lighter_client.py` 是纯只读的。需新增：`place_limit_order`、`cancel_order`、`cancel_grid_orders`、`get_open_orders`、`get_orders_history`、`place_position_stop_loss`、`cancel_tpsl`，以及 API key 签名（官方 `lighter-python` SDK 的 SignerClient）。

### 交易能力必须是显式开关，不是简单删掉保险

当前 `market_order` 与 `close_position` 直接抛 `NotImplementedError`，这是刻意的设计约束——机器人碰不到用户的本金腿。做市必然要打开这道门。

**处理方式：改为构造期的显式能力开关。** 适配器必须以 `trading_enabled=True` 构造才能下单，**默认为只读**。

这样对冲机器人继续以只读模式构造（它本就不该动 Lighter），只有做市机器人持有交易权限。一个配置错误不会让对冲机器人意外开始交易。

## 引擎解耦

`grid/grid_engine.py` 有 4 处直接访问 `self.ext._client` 取 Extended SDK 的行情与 K 线（约在 177、231、850、964 行）。这些必须收进统一适配器接口，否则引擎无法在 Lighter 上运行。

### K 线数据源

Lighter 的 `/api/v1/candlesticks` 实测返回 **403**，而趋势感知网格的 band 依赖 K 线算 ATR。

**解法：band 计算改从 Extended 取 BTC K 线。** 两所同一标的，实测基差约 $52（0.08%），用于计算 ATR 完全够用。实现上给引擎传一个独立的「行情源」参数，默认指向交易所自身，Lighter 场景下指向 Extended。

## ⚠️ 两个机器人的互锁

**最危险的组合是「做市在跑、对冲挂了」**——库存持续累积却无人对冲，等人发现时可能已是大额裸仓。

**做市机器人必须主动检查对冲机器人存活**：读 `data/lighter_hedge.jsonl` 的心跳，超过 `3 × interval` 未更新则**停止开新仓、只允许撤单**。宁可不赚，不能裸奔。

反向保险已存在：对冲机器人的 `max_primary_notional`（当前 $2,000）会拒绝跟随异常膨胀的仓位，是做市失控时的最后一道闸。

## 风控

直接继承 `grid_engine` 已有且经实盘验证的机制，不重新实现：

- 库存上限（目标 $1,500，上线期先设 $300，见「上线路径」）
- 净值回撤熔断（跌破峰值 12% 全平停机）
- 逼近强平价硬止损
- 整仓 TPSL

加上本设计新增的互锁与对冲侧的名义上限。

## 首次实盘的额外约束

用户决定跳过 dry_run 直接实盘。$300 的库存上限能限制方向性亏损，但**限制不住全新下单代码的精度错误或反复刷单**——Lighter 挂撤单免费，对账逻辑的 bug 可能几分钟刷出上千笔订单，其形态正符合 Lighter 条款禁止的 automation exploitation，可能导致积分被撤销。

**因此首次实盘必须以 `--levels 4` 启动并运行 30 分钟**（上下各 4 档而非 30 档），确认挂单价格、数量精度、撤单回收均正常后，再放开到完整档位。真出问题最多涉及 8 笔订单。

## 上线路径

1. 平掉现有 $1,500 手动仓（对冲机器人会自动平掉 Extended 对侧）
2. 交易适配器与引擎解耦完成，测试全绿
3. **`--levels 4` 小档位实盘 30 分钟**，人工核对挂单精度与撤单
4. 放开完整档位，库存上限 $300，运行 12 小时
5. 无问题则扩至库存上限 $1,500

## 明确不做（YAGNI）

- 不做多标的，只做 BTC
- 不做 Lighter 侧的 K 线获取（403，且有 Extended 代理）
- 不做做市专属的报价模型（inventory skew、adverse selection 防护等）——先用现有网格逻辑跑通，有数据再谈优化
- 不改现有 Extended 网格系统，它继续独立运行
