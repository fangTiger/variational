# 网格收益归因数据层 — 设计

日期：2026-08-11
状态：已确认，待实施

## 1. 问题

网格策略实盘跑了近一个月，但**没有人能回答「它到底赚不赚钱」**——不是数据难看，是没有数据。

现状的三个断点：

1. **闭环利润活在内存里**。`GridEngine._closed_loops` / `_realized_pnl_net` 每次重启归零，2026-08-11 一天就归零 4 次。`data/metrics.jsonl` 只有 1 行，等于没在用。
2. **跨重启的闭环会漏计**。`_loop_fills`（每格待配对成交）是纯内存 dict，重启后清空；重启前挂着的半个闭环，重启后配不上，那笔利润永远丢失。偏差方向是低估。
3. **账面收益无法归因**。权益从 $948.65 涨到 $977.33（+3.0%），但其中多少来自网格闭环、多少来自持仓方向性波动，无从区分。实测佐证：2026-08-10 有一段 8.7 小时零闭环，权益照样涨了 $8——那是纯方向性波动。

后果是所有调参都在噪音里找信号，且「再观察几天」可以无限延续。

## 2. 目标与非目标

**目标**

- 把闭环利润变成可跨重启累计、可审计的持久数据
- 把权益变动拆成「网格闭环利润」与「方向性盈亏」两部分
- 4 周内给出一个**可执行的去留结论**，且结论由系统主动推送

**非目标**

- 不做实时高频写入（每小时批量足够）
- 不做多机 / 高并发
- 不在本期做参数寻优——归因能力建立之前，调参没有意义

## 3. 判据（事先定死）

```
grid_annualized = (Σ闭环利润 ÷ 已运行天数) × 365 ÷ 本金
```

其中**本金 = 观察期第一条 `equity_snapshots` 的 `equity`**（固定值，不随权益波动而变）。观察期内若发生出入金，本金按出入金额同步调整，避免分母失真。

- 观察期 **4 周**，自数据层部署之日起算
- 满 4 周后若 `grid_annualized < 15%` → 推送通知「策略未达判据，建议停」
- 期间**每周**推送一次进度：当前年化、闭环频率、距判定剩余天数
- **只计闭环利润，不含方向性盈亏**——否则是拿运气当本事

15% 的依据：该策略承担尾部风险（卖波动率结构）又占用精力，低于此不如做别的。回测声称年化 38%，本金约 $977，maker 费为 0。

判据必须事先固定。事后定的判据永远会迁就已有数据——2026-08-06 的 α 框架就是先有模型后凑判据，最终因判据推导错误（用 `N_osc/2` 做闭环上界）而全部作废。

## 4. 架构

```
grid_engine（实盘交易进程）
  └─ 每笔成交 append 一行 → data/fills.jsonl        （改动约 5 行）

data/grid_monitor.jsonl（已有，每小时权益快照）

            │  两者都是 append-only 纯文本
            ▼
tools/pnl_attribution.py（旁路，launchd 每小时）
  ├─ 幂等增量导入 → data/grid.db（SQLite，WAL）
  ├─ 离线配对成交 → 闭环
  ├─ 计算归因指标
  └─ 达条件时推通知（复用 tools/alert_check.notify）
```

**为什么引擎只写 JSONL、不直接写库**：引擎是实盘交易进程，SQLite 写锁或磁盘异常会直接打到交易循环。append 一行纯文本是能想到的最低风险写入方式，且 DB 损坏可随时从 JSONL 全量重建。

**为什么写成交明细而非闭环**：闭环配对依赖内存态 `_loop_fills`，跨重启必然漏计（见 §1.2）。改由旁路进程从完整成交流离线配对后，配对不受重启影响，算法也能事后修正而不必改动交易进程。成交明细对后续调参同样是必需品。

## 5. 数据模型

### 5.1 `fills`（成交明细，事实表）

| 列 | 类型 | 说明 |
|---|---|---|
| `fill_id` | TEXT PK | 交易所订单 id。引擎在订单进入终态时一次性处理成交（`FILLED`，或 `EXPIRED/CANCELLED` 且 `filled_qty>0`），每个订单只产出一条记录，故订单 id 即幂等键 |
| `ts` | REAL | 成交时间戳 |
| `level` | INTEGER | 网格格号 |
| `side` | TEXT | BUY / SELL |
| `price` | REAL | 成交价 |
| `qty` | REAL | 成交数量 |
| `engine_run_id` | TEXT | 引擎本次启动的唯一标识 |

### 5.2 `closed_loops`（闭环，由 `fills` 离线配对产出）

| 列 | 类型 | 说明 |
|---|---|---|
| `loop_id` | TEXT PK | 参与配对的两个 `fill_id` 拼接，天然幂等 |
| `ts` | REAL | 后一笔成交的时间 |
| `level` | INTEGER | 格号 |
| `buy_price` / `sell_price` | REAL | 配对的两笔价格 |
| `qty` | REAL | `min(两笔数量)` |
| `gross_pnl` | REAL | `(sell_price - buy_price) × qty`，maker 费为 0 故等于净利 |

配对规则与引擎内现行逻辑一致（`grid_engine.py:1354-1380`）：同一格出现反向成交即配对，数量取小值，剩余部分留待下次配对。差异仅在于跨重启不再断裂。

### 5.3 `equity_snapshots`（权益快照）

自 `data/grid_monitor.jsonl` 导入：`ts / equity / inv_btc / inv_usd / price / mode / blocked_side`。

额外一列 `cash_flow`：标记出入金金额，默认 0。**出入金会让年化的分母失真**，必须显式标记后从收益中剔除。

### 5.4 `attribution_daily`（计算产物，每日一行）

`date / loops_n / grid_pnl / equity_change / directional_pnl / grid_annualized_to_date`

## 6. 归因算法

核心是一个恒等式：

```
权益变动 ≡ 闭环利润 + 未实现盈亏变动 + 资金费 + 出入金
```

于是：

```
方向性盈亏 = 权益变动 − 闭环利润 − 出入金
```

**这条恒等式的价值在于自证**：如果两边对不上，说明有成交漏记、资金费未计或出入金未标记。任何归因指标都必须能被它检验——上次 α 框架翻车的根因正是判据无法交叉验证。

实施要求：每次计算后校验残差。残差超过当日闭环利润的 20% 时，在报告中显式标注「归因存在缺口」，而不是静默出数。

## 7. 告警

复用 `tools/alert_check.py` 的 `notify()`（osascript 推送）。三类：

| 触发条件 | 内容 |
|---|---|
| 满 4 周且年化 < 15% | 「策略未达判据，建议停」+ 当前数值 |
| 每周一次 | 进度：当前年化、闭环频率、剩余天数 |
| 归因残差超限 | 「归因存在缺口」+ 残差金额 |

沿用既有的 6 小时同类冷却机制。

## 8. 技术选型

**SQLite，不用 PostgreSQL。** 4 周数据量约 2000 行，单机单写者。SQLite 无服务、文件即数据库、可随时从 JSONL 重建；PostgreSQL 需要额外进程、备份与连接管理，此规模下是纯负担。真需要多机时再迁移，成本也低。

启用 WAL 模式：旁路进程写入期间，面板与分析脚本仍可并发读。

## 9. 已知风险

| 风险 | 处置 |
|---|---|
| 历史闭环无法回溯 | 已丢失，不可恢复。4 周从部署日起算，不借历史数据提前出结论 |
| 出入金污染年化 | `equity_snapshots.cash_flow` 显式标记并从收益中剔除 |
| 成交明细漏记 | 由 §6 的恒等式残差校验兜底，超限即告警 |
| 单边行情淹没信号 | 库存上限维持 $5000（2026-08-11 决定）。实测库存区间 0.03x~1.89x，未接近上限。报告中同时给出方向性盈亏，便于识别噪音主导的时段 |
| 引擎 append 失败 | 包 try/except，写失败仅记日志，绝不影响交易循环 |

## 10. 测试策略

- **配对算法**：用构造的成交序列覆盖——正常配对、部分成交、跨重启、同格连续同向成交
- **幂等性**：同一份 JSONL 导入两次，行数与金额不变
- **恒等式**：构造已知的权益变动与闭环集合，验证残差为零；再注入一笔漏记，验证能被检出并告警
- **判据**：构造年化 14.9% 与 15.1% 两种数据，验证告警触发与否
- 沿用现有 pytest 套件（当前 261 passed）
